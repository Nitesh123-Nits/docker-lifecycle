Stage Deep Dive
📝
Application Stage
Write code → Dockerfile → Base image → Deps
  • 1
    Write Application Code — Your source in any language. This is the business logic that will run in the container.
  • 2
    Create Dockerfile — A plain text recipe. Each instruction maps to an image layer.
    FROM python:3.11-slim
  • 3
    Define Base Image — Smaller base = smaller attack surface. Use distroless or alpine in prod.
    FROM gcr.io/distroless/python3
  • 4
    Install Dependencies before copying code — Layer ordering matters for cache hits.
    COPY requirements.txt . && RUN pip install -r requirements.txt
  • 5
    Define Startup Command — Use ENTRYPOINT for fixed binary, CMD for overridable defaults.
    ENTRYPOINT ["gunicorn"] CMD ["app:app"]
🔨
Image Build Stage
docker build → daemon → layers → image
  • 1
    docker build sends build context (tar archive) to the Docker daemon over a Unix socket.
    docker build -t myapp:1.0 .
  • 2
    Daemon reads Dockerfile — Checks build cache for each instruction. Cache miss triggers re-execution of that layer and all subsequent layers.
  • 3
    Build Image Layers — Each instruction produces a content-addressed read-only layer stored in OverlayFS. Layers are shared across images.
  • 4
    Final Image — A manifest.json listing all layer digests + config (env vars, cmd, labels). Stored in /var/lib/docker/overlay2.
📦
Image Storage Stage
Tag → Push → Registry distribution
  • 1
    Tag the Image — Tags are mutable pointers to immutable image digests. Use semantic versioning.
    docker tag myapp:1.0 org/myapp:v1.0.3
  • 2
    Push to Registry — Only layers not already present in registry are uploaded. Content-addressing enables dedup.
    docker push org/myapp:v1.0.3
  • 3
    Registry options — Docker Hub (public), AWS ECR (private, IAM-integrated), GCR, Harbor (self-hosted), GitHub Container Registry.
⚡
Container Runtime Stage
docker run → pull → create → allocate → start
  • 1
    docker run — CLI sends request to dockerd via /var/run/docker.sock. Daemon delegates to containerd.
    docker run -d -p 8080:80 --memory=512m myapp
  • 2
    Image Pull — containerd pulls missing layers from registry, extracts to overlay2 storage.
  • 3
    Allocate Resources — cgroups v2 enforces CPU (shares/quota) and memory limits. OOM killer activates if limit exceeded.
  • 4
    Network Setup — runc creates veth pair, assigns container end to docker0 bridge, sets up NAT (iptables MASQUERADE).
  • 5
    Start Process — runc calls clone() syscall with namespace flags. Your CMD becomes PID 1 in the new namespaces.
🔒
Execution & Isolation
Namespaces + cgroups + seccomp
  • 1
    Linux Namespaces — 7 namespace types isolate process visibility: PID, NET, MNT, UTS, IPC, USER, TIME.
  • 2
    Shared Host Kernel — No guest OS or hypervisor. Container sees its own process tree but all processes run on the same kernel.
  • 3
    seccomp profiles — Docker applies a default seccomp filter blocking ~44 dangerous syscalls (ptrace, reboot, etc.).
  • 4
    App is accessible — Port mappings via iptables DNAT rules route traffic from host:port to container IP:port.
🛑
Stop & Remove
Graceful shutdown → cleanup → image persists
  • 1
    docker stop — Sends SIGTERM to PID 1. Default 10s grace period for graceful shutdown, then SIGKILL.
    docker stop -t 30 <container_id>
  • 2
    docker rm — Removes the writable container layer from disk. Metadata and network cleanup. Image layers untouched.
    docker rm <container_id>
  • 3
    Image persists — Base image layers remain in local cache. Use docker rmi to remove image. docker system prune for full cleanup.

🧱 OverlayFS & Image Layers

Docker images are stacked read-only layers on OverlayFS. When a container starts, a thin writable layer is added on top.

Files are read from the uppermost layer that contains them. Writes go to the container layer (copy-on-write).

Interview Q&A
EasyWhat is the difference between a Docker image and a Docker container? ▶

A Docker image is a read-only template — a stack of immutable layers stored on disk, defined by a Dockerfile. It's like a class or blueprint. It has no running process and takes no CPU or memory.

A Docker container is a running instance of an image. When you run docker run, Docker adds a thin writable layer on top of the image layers and starts a process inside it. Multiple containers can share the same underlying image layers simultaneously (copy-on-write semantics).

Analogy: Image = class definition. Container = object instantiated from that class.

EasyWhat happens when you run docker run? ▶

1. Docker CLI sends a REST request to dockerd via the Unix socket at /var/run/docker.sock.

2. dockerd checks if the image exists locally. If not, it pulls from the registry via containerd.

3. containerd creates a container specification (OCI bundle) and delegates to runc.

4. runc calls the Linux clone() syscall with namespace flags (PID, NET, MNT, UTS, IPC), setting up isolation. cgroups are configured for resource limits.

5. OverlayFS mounts the image layers (lowerdir) with a new writable layer (upperdir).

6. The network namespace is connected to the docker0 bridge via a veth pair.

7. Your CMD or ENTRYPOINT starts as PID 1 inside the container.

MediumHow does Docker achieve isolation? Explain namespaces and cgroups. ▶

Namespaces provide isolation by giving each container its own view of system resources. Key namespaces: PID (container sees its own process tree, its app is PID 1), NET (own network stack, interfaces, routing table), MNT (own filesystem mount points), UTS (own hostname), IPC (own shared memory and semaphores), USER (UID/GID mapping — root in container ≠ root on host).

cgroups v2 enforce resource limits. While namespaces control what a process can see, cgroups control how much it can use. Docker applies cgroup constraints for CPU quota (cpu.max), memory hard limit (memory.max), and PID count (pids.max). Exceeding the memory limit triggers the OOM killer.

Together, namespaces give isolation of visibility; cgroups give isolation of consumption.

MediumExplain Docker layer caching and how to optimize it. ▶

Each Dockerfile instruction creates a layer. Docker caches these layers using a content hash. If an instruction and its inputs haven't changed since the last build, Docker reuses the cached layer (cache hit).

Critical rule: A cache miss on any layer invalidates all subsequent layers. So instruction order matters enormously.

Optimization pattern: Copy dependency manifests first, install them (these change rarely), then copy app code (changes frequently):

COPY requirements.txt . → RUN pip install -r requirements.txt → COPY . .

This way, a code change only busts the last COPY layer, not the slow pip install layer. This can reduce rebuild time from minutes to seconds.

MediumWhat is a multi-stage build and why is it important? ▶

Multi-stage builds allow you to use multiple FROM instructions in a single Dockerfile. The key benefit: you can use a heavy build environment (with compilers, SDK, test tools) but copy only the compiled artifacts into a minimal runtime image.

Example: Stage 1 uses golang:1.21 to compile a binary. Stage 2 uses FROM scratch (literally empty) and just COPY --from=0 /app/binary /binary. Final image is just a few MB instead of hundreds.

Benefits: Dramatically smaller images → faster pulls, less attack surface, lower storage costs. Build secrets (API keys used during build) don't leak into the final image.

HardHow does OverlayFS work internally for Docker containers? ▶

OverlayFS is a union filesystem that merges multiple directory trees into a single view. Docker uses it as its default storage driver (overlay2).

Structure: Image layers are the lowerdir stack (read-only). The container's writable layer is the upperdir. The workdir is used by OverlayFS for atomic operations. The merged directory is the unified view presented to the container.

Read path: OverlayFS looks up files from upperdir first, then falls through to lowerdir layers top-to-bottom. This is O(n) for deep layer stacks.

Write path (Copy-on-Write): Writing to an existing file copies the entire file from lowerdir to upperdir first, then modifies it. This means large files are expensive to modify — even a 1-byte change copies the whole file. This is a known limitation called write amplification.

Delete path: Deleting a file creates a "whiteout file" in upperdir that masks the file in lowerdir. The file appears deleted in the merged view but the original layer is unchanged.

HardWhat is the dockerd → containerd → runc architecture? Why was it decomposed? ▶

Originally Docker was a monolith. It was decomposed for several reasons: OCI standardization, Kubernetes compatibility, and daemon stability.

dockerd: High-level daemon handling the Docker API, image management, build, volume/network management. Most users interact with this layer.

containerd: OCI-compliant container runtime managing the lifecycle of containers: create, start, stop, delete, snapshot. Kubernetes uses containerd directly, bypassing dockerd entirely.

containerd-shim: A per-container process that stays alive even if containerd is restarted. This makes containers "daemonless" — they survive daemon upgrades without restarting.

runc: The lowest-level OCI runtime. Just responsible for creating the container: setting up namespaces, cgroups, and executing the init process via Linux syscalls. Exits after container starts.

This decomposition means Kubernetes can use containerd directly without Docker at all, which is why many managed K8s services removed the Docker shim in favor of direct containerd or cri-o.

HardHow does docker stop work? Why is signal handling in PID 1 critical? ▶

docker stop sends SIGTERM to PID 1 inside the container, then waits a configurable grace period (default 10s). If the process hasn't exited, it sends SIGKILL.

The PID 1 problem: In Linux, PID 1 has special behavior. Unlike other processes, PID 1 does not receive signals it hasn't explicitly handled — the default signal handlers (including for SIGTERM) are ignored by the kernel for PID 1.

If your app doesn't handle SIGTERM explicitly (e.g., a raw python app.py as CMD), it will ignore the signal and get SIGKILL'd after the grace period, preventing graceful shutdown (in-flight requests dropped, no DB connection cleanup).

Solutions: Use exec form of CMD (not shell form) so your app is PID 1, not a shell. Use a proper init system like tini (docker run --init). Implement SIGTERM handler in your application code.
